# 改枪方案 Discord Bot 同步 — 原型说明

## 文件说明

| 文件 | 说明 |
|------|------|
| `index.html` | 改枪码推荐管理端列表页（模拟线上已有页面），入口跳转到同步管理页 |
| `sync-manager.html` | **Discord 同步管理页**（本次迭代核心） |
| `styles.css` | 共用样式，遵循 `/design.md` 直角军事风格规范 |
| `DISCORD_SYNC_PRD.md` | 需求文档，当前最新版本 |
| `technical-flow.drawio` | 技术方案流程图（方案发布流程 + 帖子数据回收流程），可用 [draw.io](https://app.diagrams.net/) 打开 |
| `CMS_STRUCTURE_CAPTURE.md` | 对真实 CMS（`playdeltaforce-cms.levelinfiniteapps.com/gun-codes`）页面结构与 API 的抓取记录 |

## 如何预览

直接用浏览器打开 `index.html` 或 `sync-manager.html`（纯静态文件，无需启动服务）。数据存储在 `localStorage`，刷新不丢失，可通过浏览器清除站点数据重置为初始示例。

## 版本演进

- **v1**：基础流程，选择方案 → 确认发布 → 发帖历史。
- **v2**：基于真实 CMS 数据量级（74+ 条方案），补充了发布频次限流、每日额度、最大勾选数、频道容量预警、无互动自动归档等"规模化治理"机制。
- **v3**：产品侧对 v2 三点纠偏后简化：
  1. **删除"高优先级"逻辑**——`priority`/`sortOrder` 字段只是工具站内的展示排序，不代表紧急程度，不应参与发布决策。列表中改名为"站内排序"，仅展示。
  2. **发布节流改为纯前端硬性拦截**——去掉"发送间隔""排队到次日"等后台调度概念；单次最大勾选数、每日发送上限，超出直接不允许提交，不做任何延迟/排队处理。
  3. **删除容量预警与自动归档**——Discord 论坛本身靠帖子活跃度自然排序（有回复的帖子会靠前），不需要管理端做"堆积预警"或"无互动自动归档"。「归档」按钮简化为纯粹的运营手动记录工具。
- **v3.1**：进一步简化：
  1. **删除快捷选择中的"近7天更新"**——仅保留"全部未同步"一个快捷按钮。
  2. **删除发帖历史的"归档"操作**——该按钮此前只是把状态改成"已归档"这个本地标签，不对 Discord 帖子做任何实际处理，保留它没有实际意义。历史状态机简化为：执行中 / 已完成 / 失败。
- **v4**：明确初版范围边界：
  1. **多语言检查改为按方案×频道自动跳过**——缺失日语内容的方案，其 Japan 消息自动跳过，不影响该方案的 Global 消息，也不影响其他方案；不再用"整批仅发 Global"的确认弹窗强制降级（v3 的方式会误伤本次一起选中的、原本有日语内容的其他方案）。额度计数、发布预览、实际发送三处口径统一。
  2. **明确初版不做已发布帖子的关联管理与编辑**——不做"方案与帖子强一对一校验"，不做"内容漂移检测"（方案改了不会提示帖子过期），不做"编辑原帖"。每次发布都是独立的一次性发送，重复发布只做信息提示不做阻塞。这部分能力列入 PRD 后续可扩展方向。
- **v4.1**：补充发帖历史筛选/排序、新增技术方案章节：
  1. **发帖历史列表增加筛选与排序**——支持按关键词（方案名称/方案ID/任务ID）、频道、状态筛选，支持按发送时间（新/旧）、点赞数、评论数排序。
  2. **新增技术方案章节**——用流程图（`technical-flow.drawio`）说明实现路径，分为「方案发布流程」与「帖子数据回收」两个阶段，明确方案文本处理规则（多语言取值、配件树扁平化）、同步到 Discord 的方式、以及点赞/评论数据的定时回收机制。
  3. **PRD 正文精简为面向开发的指导性文档**——去除背景介绍与历次版本迭代说明，只保留当前生效的需求本身；语气从"描述性说明"调整为"要做什么/不做什么"的明确指令。
- **v4.2**：删除方案列表的快捷选择区域——不再提供"全部未同步"等快捷勾选按钮，运营只能逐条手动勾选或使用「全选」，避免因批量快捷操作误选到不该同步的方案。
- **v4.3**：新增发布前二次确认弹窗——在原有的"确认发布到 Discord"弹窗之后，点击「确认并发布」不再直接执行发布，而是先弹出第二层风险确认弹窗，要求运营手动输入指定短语（"确认发布到改枪频道"）且完全匹配后才能点击「确认发布」，真正触发发送逻辑。目的是防止手滑误操作将方案发布到外网可见的 Discord 频道。
- **v4.4**：优化发帖历史列表宽度适配——原列表 10 列过多，在标准容器宽度下需要横向滚动才能看全。将"任务ID"与"方案ID"合并进"方案"列（同格上下两行展示），将"点赞"与"评论"合并为一列"互动"，列数从 10 列精简为 7 列，容器宽度内即可完整展示，不再需要横向滚动。
- **v4.5**：进一步调整发帖历史列表字段：
  1. **任务ID 收窄**——不再跟方案信息共占一列的展示宽度，单独设为窄列，内容过长时截断并通过 hover 提示完整值。
  2. **方案ID 与任务ID 拆分为两列**——v4.4 中曾把两者合并进同一格展示，现改为各自独立成列，避免信息混杂在一起不好辨识。
  3. **新增"实际发送时间"列**——新增 `sentAt` 字段，记录 Bot 真正调用 Discord API 完成发送的时间，与"发送时间"（任务创建/入队时间 `executeAt`）区分开，用于体现消息队列中的排队延迟。由于列数增加，列表恢复为允许横向滚动。
- **v5.0**：取消每日发送数量的硬性拦截，改为纯统计展示：
  1. **不做每日发送数量的前端/后台拦截**——原因：后台存在异步发送队列，若仅按"当日已创建任务数"在前端计数拦截，任务的真实执行时间可能跨天（如 23:59 提交、次日凌晨才真正发出），会导致统计口径与实际发送情况脱节，甚至可能在跨天时因队列积压叠加导致短时间内发出过量帖子。综合评估后，本版本不再对发送数量做任何硬性拦截，完全交由运营自行判断发布节奏。
  2. **顶部统计条改为按频道拆分展示**——原"今日额度：已用 X / 上限 Y"进度条替换为两组独立统计：**Global 今日已发 X 条**、**Japan 今日已发 X 条**，不做频道间的合计，也不设上限、不需要配置每日发送上限参数。
  3. **确认发布弹窗内的额度提示改为纯信息展示**——按频道展示本次待发送数量，仅供参考，不再置灰「确认并发布」按钮；重试操作也不再受额度限制。
  4. 单次操作最大勾选数（100 条/次）保留，与每日发帖统计是两套独立逻辑，不受本次调整影响。
- **v5.1**：确认发布弹窗内的数量提示，从只展示"本次待发送数量"调整为按已选中频道分别展示**"今日已发数量 + 本次发布数量"**（如"Global 今日已发 5 条，本次发布 3 条"），与顶部统计条口径统一，仍仅作信息提示不做拦截。
- **v5.2（当前）**：发帖历史新增"批次ID"字段：
  1. **新增 `batchId` 字段**——一次点击「确认并发布」为一个批次，本次产生的所有帖子任务共享同一个批次ID。批次ID不影响任务本身的重试/删除等操作逻辑。
  2. **发帖历史列表新增"批次ID"列**——仅作独立展示，供运营人工比对同一次提交产生的其他帖子；关键词搜索同步支持匹配批次ID。曾评估过"按批次聚合/展开收起"的交互方案，考虑到实际收益不明确、增加了不必要的交互复杂度，最终决定不做聚合分组，只加一列即可满足查阅需求。

## 关于"每日发帖数量"逻辑的取舍说明

产品侧最初考虑过更严谨的额度校验方案（前端计数 vs 后台实际发出数校验的取舍、跨天队列执行导致的统计偏差、后台有任务执行时前端是否允许创建新任务等问题），评估后认为：在后台是异步队列执行的架构下，任何单纯依赖前端计数的硬性拦截都无法准确反映真实发送情况，容易在跨天时失真；而做后台强校验又涉及"前端如何感知并展示后台校验结果"的复杂交互。综合权衡后，v5.0 选择放弃拦截，仅做统计展示，把发布节奏的把控完全交给运营人工判断，这是当前版本最简单、最不容易出现统计偏差的做法。

## 与真实 CMS 的对齐点

详见 `CMS_STRUCTURE_CAPTURE.md`。核心结论：
- 真实方案数据量级远超早期原型中的 10 条示例（烽火模式即有 74 条），因此需要基本的快捷筛选辅助批量操作。
- CMS 源数据已有 `priority`（仅站内排序用）/ `sync_status` / `synced_at` 字段，原型已对齐澄清后的字段语义。
- CMS 支持 14 种语言（`i18n`），当前原型仍只做 Global/Japan 两个频道示例，为「后续可扩展更多语言频道」预留了设计空间。
