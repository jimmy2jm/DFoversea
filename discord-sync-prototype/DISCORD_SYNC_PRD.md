# 改枪方案 Discord Bot 同步 — 需求文档

## 一、功能说明

在改枪码管理端新增「Discord 同步管理」页面，运营在此页面手动选择改枪方案、选择目标 Discord 频道（论坛型频道），提交后由 Bot 将方案转换为 Discord 消息格式并发送。同步动作**必须由运营主动触发**，方案的新增或修改不触发自动推送。

每个改枪方案在每个目标频道下，都必须作为**一条独立的 Discord 消息（Embed）**发送，不允许将多个方案合并进同一条消息。

---

## 二、方案选择与筛选

### 2.1 方案选择方式

方案列表**不提供任何快捷勾选按钮**（如"全部未同步"），运营需逐条手动勾选，或使用「全选」勾选当前 Tab 下的全部方案。列表提供按方案名称、方案ID的筛选输入框，辅助运营缩小查找范围，但筛选结果仍需运营手动勾选，不提供"筛选后自动全部勾选"之类的联动。

### 2.2 站内排序字段

方案数据中的 `sortOrder` 字段（原 CMS 字段名 `priority`）仅用于列表展示排序，**不代表方案的紧急程度或重要性**。该字段只做列表展示（列名显示为"站内排序"），不能作为任何选择逻辑或发布逻辑的判断依据。

### 2.3 单次操作数量上限

- 单次发布最多勾选 **100 条**方案（数值需可在「发布策略」配置面板中调整）。
- 勾选数超过上限时，点击「发布到 Discord」需直接拦截，**不允许打开确认弹窗**，并提示"请减少勾选后再发布"。
- 该校验仅在前端进行，不涉及后端队列或分批处理机制。

---

## 三、多语言发送规则

### 3.1 频道与语言对应关系

当前需支持两个 Discord 频道：

| 频道 | 语言 | 说明 |
|------|------|------|
| Global | 英语 | 必填，工具站录入方案时应保证英语内容存在 |
| Japan | 日语 | 非必填，独立的 Discord server，方案数据中以 `jp` 字段标识是否存在日语内容 |

### 3.2 发送规则：按"方案 × 频道"逐一判断

对每一个被选中的方案，在每一个被选中的频道下，需要单独判断是否生成一条待发消息：

```
频道 = Global → 始终生成一条待发消息
频道 = Japan  → 仅当该方案的 jp 字段存在有效内容时才生成待发消息；
                若不存在，则跳过该条消息，不生成、不计入发送数量
```

跳过某方案的 Japan 消息，**不能影响**：
- 该方案在 Global 频道的消息（必须正常生成并发送）
- 其他方案在 Japan 频道的消息（必须正常生成并发送）

即裁剪粒度必须精确到单条"方案 × 频道"组合，不允许因为批次中存在缺失日语的方案，就把整批选中方案都降级为仅发 Global。

### 3.3 交互要求

- 确认发布弹窗中，Japan 分组只渲染实际有日语内容的方案；缺失日语的方案不出现在 Japan 分组里（不是展示后置灰或删除线）。
- 弹窗内需要展示一条提示，告知本次因缺失日语被跳过的方案名单，例如："以下方案缺失日语多语言配置，将自动跳过其 Japan 频道消息（其余频道正常发送）：xxx"。该提示**仅作信息告知，不阻塞提交**，不需要运营做二次确认或选择。
- 消息总数统计必须基于"实际会发送的消息数"（即已经排除被跳过的 Japan 消息之后的数量）进行计算。

## 四、每日发帖统计（按频道展示，不设上限）

### 4.1 逻辑

不做每日发送数量的硬性拦截。原因：后台存在发送队列，Bot 是异步拉取任务执行的，如果仅在前端按"当日已创建任务数"计数拦截，会出现以下问题：
- 运营在 23:59 提交的一批任务，可能排到 Bot 队列里在次日 00:01 才真正执行发送，前端按"提交时间"计数会把这批算进前一天，实际却是第二天发出，导致次日统计与真实发送量不一致，甚至可能出现"当日校验通过，但排队执行时叠加了大量前一天遗留的任务，导致短时间内发出过量帖子"的情况。
- 前端只能看到"任务是否被创建"，无法感知后台队列的真实执行进度，因此不适合作为发送数量的硬性拦截依据。

综合评估后，**当前版本不做任何每日发送数量的拦截**（前端不拦截，后台也不因为数量做限流），完全交由运营自行判断发布节奏。页面仅做**统计展示**，帮助运营了解当天已经发了多少条，自行决定是否要控制频次。

### 4.2 统计口径

- 统计维度按 **频道** 拆分，分别统计 **Global** 和 **Japan** 当日已发送的消息数量，不做合计展示。
- 计数对象为"已进入发送队列的任务"（即 `executeAt` 落在今天的任务），不等待任务真正执行完成，因为这是当前版本唯一能稳定获取的时间点。
- 统计数值**不设上限**，不需要配置"每日发送上限"参数，也不需要百分比进度条一类的"逼近上限"视觉提示。
- 统计每日按自然日重置（次日 0 点，具体时区口径待确认，见第九章）。

### 4.3 页面展示

- 顶部常驻展示两个独立的统计值：**Global 今日已发 X 条**、**Japan 今日已发 X 条**。
- 旁边附一行说明文案，明确告知运营"仅作数量统计，不设发送上限，需自行把控发布频次"。
- 确认发布弹窗内，按已选中的频道分别展示"今日已发数量 + 本次待发送数量"（如：🌐 Global 今日已发 5 条，本次发布 3 条 · 🇯🇵 Japan 今日已发 2 条，本次发布 2 条），口径与顶部统计条一致，供运营在提交前做参考，**不做任何拦截**，「确认并发布」按钮不会因为数量原因被置灰。未勾选的频道不展示对应行。

### 4.4 单次操作数量上限（保留，与每日统计无关）

- 单次发布最多勾选 **100 条**方案（数值需可在「发布策略」配置面板中调整）。
- 勾选数超过上限时，点击「发布到 Discord」需直接拦截，**不允许打开确认弹窗**，并提示"请减少勾选后再发布"。
- 该校验仅在前端进行，与每日发帖统计无关，也不涉及后端队列或分批处理机制。这是为了防止运营误操作全选后一次性提交巨量任务，与"控制每日发帖频率"是两个不同目的的校验，需要分开理解，不要合并成同一套逻辑。

## 五、发帖历史

### 5.1 状态机

历史记录只需维护三种状态，**不需要**"已归档""排队中"等其他状态：

| 状态 | 说明 |
|------|------|
| 执行中 | Bot 正在调用 Discord API 发送 |
| 已完成 | 发送成功，帖子在 Discord 上可见 |
| 失败 | Discord API 报错，需保留错误原因，支持手动重试 |

- **失败重试**：不受每日发帖统计影响（该统计不做拦截），点击重试后重新进入发送队列。
- **删除记录**：仅清除本地历史记录，不需要（也不能）联动删除 Discord 侧已发送的帖子。删除操作只针对单条帖子记录，不提供"删除整个批次"的批量操作；如需清空一个批次，运营需逐条删除该批次下的每条记录。

### 5.2 批次ID字段

一次点击「确认并发布」算作**一个批次**，同一批次内可能因勾选了多个方案、多个频道而产生多条帖子任务（数量 = 实际会发送的"方案 × 频道"组合数，见第三章）。

每条帖子任务需要额外记录一个 **批次ID（batchId）**，同一次提交产生的所有帖子任务共享同一个批次ID。批次ID仅作为发帖历史列表中的一个独立展示列，供运营查阅"哪些帖子是同一次提交产生的"，**不需要**基于批次ID做任何聚合分组、展开/收起等交互——按批次聚合展示的方案已评估后确认不做，实际收益不明确，保留字段本身即可满足关联查阅的需求。

批次ID不影响任务本身的执行、重试、删除逻辑，单条任务的操作永远只针对它自己。重试失败任务时沿用原有的批次ID，不生成新的批次ID。

早期版本产生的历史数据没有批次ID，该列直接显示"-"，不需要做数据迁移或补录。

## 六、页面结构

### 6.1 同步管理页

| 区域 | 要求 |
|------|------|
| 顶部发帖统计条 | 常驻展示 **Global 今日已发 X 条**、**Japan 今日已发 X 条**两组独立统计（按频道拆分，不做合计，不设上限），附一个齿轮按钮打开「发布策略」配置面板（见第四章） |
| Tab 栏 | 烽火方案 / 战场方案 / 发帖历史，按方案模式区分 |
| 筛选区 | 按方案名称、方案ID筛选 |
| 方案列表 | 表格展示方案，支持逐条勾选与「全选」，"站内排序"列仅做展示，不参与任何逻辑判断；**不提供任何快捷勾选按钮** |
| 底部按钮 | 「发布到 Discord」按钮；未勾选任何方案或当前处于「发帖历史」Tab 时，需隐藏/禁用该按钮 |

### 6.2 确认发布弹窗

弹窗需包含以下模块：

1. **频道选择区**：Global / Japan 标签多选
2. **消息数量提示**：按已选中的频道分别展示"今日已发数量 + 本次待发送数量"（如"🌐 Global 今日已发 5 条，本次发布 3 条 · 🇯🇵 Japan 今日已发 2 条，本次发布 2 条"），**仅作信息提示，不做任何拦截**，「确认并发布」按钮不会因为数量原因被置灰（见第四章）
3. **日语缺失提醒**：告知哪些方案的 Japan 消息被自动跳过（见第三章），仅作信息提示，不阻塞发布
4. **重复发布提醒**：若选中方案中包含已发布过的方案，需提示"该方案此前已发布过，确认后将创建新的帖子"；该提示仅作信息告知，不单独做拦截或二次确认（统一走 6.3 的二次确认弹窗）
5. **消息总数**（按实际会发送的数量计算）+ 已选频道标签
6. **预览卡片（可滚动）**：按频道分组展示待发消息内容，Japan 分组只展示实际有日语内容的方案

点击「确认并发布」按钮，**不直接执行发布**，需先关闭当前信息后打开 6.3 的二次确认弹窗。

### 6.3 二次确认弹窗（发布前风险确认）

**目的**：Discord 改枪频道对外网玩家可见，一旦误发布无法像内部工具一样简单撤回。因此在真正调用发布前，需要设置一道额外的人工确认关卡，防止运营手滑点错按钮导致误发布。

**交互要求**：

1. 弹窗内提示风险文案，例如："该操作将把消息发布到 Discord 改枪频道（外网玩家可见），请再次核对后确认。"
2. 展示一段指定的确认短语，例如：**"确认发布到改枪频道"**（具体文案可调整，但需明确、不易误输入）。
3. 提供一个输入框，运营需**手动输入与指定短语完全一致的文本**。
4. 「确认发布」按钮默认置灰禁用；仅当输入框内容与指定短语**完全匹配**（含标点、空格，逐字比对）时，按钮才可点击。
5. 输入框内容有任何变化（包括从匹配变为不匹配）都需要实时重新校验按钮的可点击状态。
6. 点击「取消」或关闭弹窗，需清空输入框内容，不保留上次输入。
7. 点击「确认发布」后才真正触发第四、五章描述的发布逻辑（生成同步任务、调用发布），并关闭本弹窗与上一层的确认发布弹窗。
8. 从第一层确认弹窗打开到本弹窗完成确认，中间可能经过一段时间，实际执行发布前需**重新确认本次仍有可发送的消息**（防止这段时间内勾选状态被清空导致空提交）；由于不做数量拦截，无需重新校验额度。

### 6.5 发帖历史列表

| 列 | 说明 |
|----|------|
| 方案 | 方案名称（枪械 · 方案名） |
| 方案ID | 独立一列，与任务ID、批次ID分开展示 |
| 任务ID | 独立一列，列宽较窄；内容较长时做单行截断（`text-overflow:ellipsis`），完整值可通过 `title` 悬浮提示查看，不与方案ID/批次ID共列 |
| 批次ID | 独立一列，标识该条帖子来自哪一次提交（见 5.2）；同一批次的多条记录会展示相同的批次ID，方便运营人工比对同批次的其他帖子；仅作展示，不提供点击筛选/跳转等交互 |
| 频道 | Global / Japan |
| 发送时间 | 任务被创建 / 进入队列的时间（对应 `executeAt`） |
| 实际发送时间 | Bot 真正调用 Discord API 完成发送的时间（对应 `sentAt`），与"发送时间"分列展示，用于体现消息队列中的排队延迟；仅"已完成"状态有值，"执行中""失败"状态该列显示"-" |
| 消息链接 | 可跳转到对应消息 |
| 互动 | 👍 点赞数 · 💬 评论数合并展示在一列（Discord 帖子反应数快照，回收机制见第七章 7.3） |
| 状态 | 执行中 / 已完成 / 失败 |
| 操作 | 重试（仅失败状态可用，重新进入发送队列，不受每日发帖统计限制）/ 删除（仅清除本地记录） |

列数较多，允许表格在容器宽度不足时出现横向滚动；"方案"列使用弹性宽度吸收剩余空间，"方案ID""任务ID""批次ID"等信息密度较低的列使用固定窄宽度。列表按帖子逐条平铺展示，**不做任何按批次的聚合分组或展开/收起**——该方案已评估后确认不做，运营如需查看同一批次的其他帖子，可直接通过"批次ID"列人工比对或结合关键词搜索查找。

需在列表上方提供筛选与排序区：

| 筛选/排序项 | 说明 |
|------------|------|
| 关键词搜索 | 同时匹配方案名称、方案ID、任务ID、批次ID，任一命中即显示 |
| 频道筛选 | 全部 / Global / Japan |
| 状态筛选 | 全部 / 执行中 / 已完成 / 失败 |
| 排序 | 发送时间（最新在前，默认）/ 发送时间（最早在前）/ 点赞数从高到低 / 评论数从高到低 |

筛选与排序需支持组合使用（例如：频道=Japan + 状态=失败 + 按发送时间最新排序）。

### 6.6 发布策略配置面板

| 配置项 | 默认值 |
|--------|--------|
| 单次操作最大勾选数（条/次） | 100 |

该项为前端提交前的硬性校验，**不需要**实现后台排队、延迟发送、限流间隔等后端调度机制。每日发送数量不在此面板配置，因为不设上限，仅在顶部做统计展示（见第四章）。

## 七、技术方案

整体实现路径见流程图：`technical-flow.drawio`（可用 [draw.io](https://app.diagrams.net/) 打开），分两个阶段：**方案发布流程**（同步触发）与**帖子数据回收**（异步定时任务）。以下按阶段说明各环节的实现要点。

### 7.1 方案发布流程

```
CMS 方案数据
  → 同步管理页：运营勾选方案 + 选择频道
  → 前端硬性校验（单次上限 / 多语言自动跳过，见第二、三章）
  → 生成批次ID batchId（本次提交的唯一标识，见 5.2）
  → 生成同步任务（方案ID × 频道，逐条独立，均携带同一个 batchId）
  → 任务队列（待执行）
  → Bot 拉取任务
      → 方案文本处理（见 7.2）
      → 组装 Discord Embed JSON
      → 调用 Discord API 发送
      → 成功：写回发帖历史（状态=已完成，记录 message_id / thread_id、实际发送时间 sentAt）
      → 失败：写回发帖历史（状态=失败，记录错误原因，支持人工重试）
```

任务生成时记录的时间（`executeAt`，即列表"发送时间"列）与 Bot 真正调用 Discord API 完成发送的时间（`sentAt`，即列表"实际发送时间"列）需分开存储：两者之间可能因队列排队、限流退避等原因存在延迟，不能假定两个时间相同。

`batchId` 需要在生成任务这一步就写入每条任务记录，不能后补——它是发帖历史列表"批次ID"列的展示依据。重试失败任务时沿用原有的 `batchId`，不生成新批次。

任务队列与 Bot 拉取任务之间的具体形式（消息队列 / 数据库表轮询）由开发根据现有 Bot 服务架构自行选型，本文档不做限定。

### 7.2 方案文本处理规则

Bot 从 CMS 方案数据转换为 Discord Embed 时，需要完成以下处理：

1. **按目标频道取对应语言内容**：
   - Global 频道：取方案的英语内容（`i18n.en` 或方案主字段，具体以 CMS 实际返回字段为准）
   - Japan 频道：取 `i18n.ja` 字段内容
2. **配件树扁平化摘要**：`config_data.guncode_result.components` 是嵌套树结构，不能直接整树塞进消息。需要设计"展示哪些核心 slot"的规则（例如只取一级 slot 的 `attachment_info.name`，忽略嵌套子件，最多展示 5-6 个核心部位），具体展示哪些部位需与视觉/文案确认（见第九章）。
3. **字段映射**：方案名称 → Embed title；`image_url` → Embed image；改枪码 → Embed field（代码块样式）；`tags_snapshot` → Embed footer 或标签展示；作者信息 → Embed author。

### 7.3 帖子数据回收方式（阅读量 / 互动量 / 点赞量）

发帖历史列表中的 👍 点赞 / 💬 评论数据，通过**独立于发布流程的定时任务**回收，不在发布成功的瞬间获取（因为帖子刚发出时互动数据必然为 0，需要后续持续更新）：

```
定时任务触发（如每 30 分钟一次，具体频率由开发根据 Discord API 限流情况确定）
  → 扫描发帖历史中「状态=已完成」的记录，取出各条的 message_id / thread_id
  → 调用 Discord API：
      - 获取帖子首帖消息详情（含 reactions 数组）
      - 获取帖子内回复消息列表（用于统计评论数）
  → 回写发帖历史对应记录的 reactionCount（点赞）/ commentCount（评论）字段
  → 发帖历史列表下次渲染时展示最新数值
```

**说明**：
- Discord 原生没有"阅读量"概念（论坛帖子不提供浏览计数 API），因此本次不做阅读量回收，仅回收点赞（reaction）与评论（回复消息数）两项。
- 该定时任务只需处理「状态=已完成」的记录，「失败」「执行中」状态的记录没有对应的 Discord 消息，跳过即可。
- 若单次扫描的帖子数量较大，需自行处理 Discord API 的限流（429），建议加入基础的重试与退避机制，具体实现由开发把控，不在本文档约束范围内。

## 八、初版范围声明（本次不实现）

初版的目标是打通"管理端方案 → 转换为 Discord 消息格式 → 成功发出"这一条链路，以下能力**本次不实现**，开发时无需考虑，也无需为后续扩展预留复杂的数据结构：

- **不做方案与帖子的一对一校验**：不需要校验某个 (方案, 频道) 是否已存在一条"当前生效"的帖子，每次点击发布都是一次独立的发送动作。
- **不做内容漂移检测**：方案在管理端被编辑后，不需要与已发布的帖子内容做比对，不需要在列表页标记"待更新"之类的状态。
- **不做编辑已有帖子**：发布动作只创建新的 Discord 消息，不需要调用 API 编辑此前已发送的消息内容。
- **不做"发新帖 / 编辑原帖"的选择弹窗**：运营重新同步某方案时不需要做任何模式选择，直接生成新消息即可。

由此产生的行为（需告知运营，但不需要开发额外处理）：
- 同一方案可以被反复点击发布，每次都会在 Discord 上产生一条新消息，不会覆盖或替换旧消息。
- 方案数据被修改后，已发布的旧帖子内容不会自动更新，系统不提供任何"帖子内容已过期"的提示机制。

这部分能力已整理为后续可扩展方向，见第十章，本次不排期。
